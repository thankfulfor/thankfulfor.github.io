## Контекст

[PastVu](https://pastvu.com/) — открытый архив исторических фотографий и картин. Внешние приложения получают данные через публичный HTTP API, а клиент самого PastVu использует также внутренние Socket.IO actions.

Работа началась с небольшого дополнения одного публичного метода. После проверки реальных ответов выяснилось, что справочнику не хватает не только примеров, но и описания общих правил: транспорта, структуры ответа, обработки ошибок и формирования URL изображений. Более сложные методы потребовали отдельного контрактного аудита.

Параллельно я исследовала внутренний Socket.IO action, контракт которого не был вынесен в типы или машиночитаемую схему. Так получились два связанных направления: развитие официальной документации для внешних разработчиков и восстановление внутреннего контракта для команды проекта.

## Публичный REST API

В [публичном справочнике PastVu API](https://docs.pastvu.com/dev/api) описаны методы, к которым внешние клиенты обращаются через `https://api.pastvu.com/api2`. Я последовательно дополнила все четыре метода из официального списка и добавила общие правила выполнения запросов.

| PR | Что добавлено |
|---|---|
| [`#77`](https://github.com/PastVu/docs/pull/77) · `photo.giveForPage` | Пример ответа, ключевые поля и ошибки метода, который возвращает данные страницы снимка. |
| [`#78`](https://github.com/PastVu/docs/pull/78) · `photo.giveNearestPhotos` | Параметры поиска, фильтрация, пагинация, структура результата и порядок координат. |
| [`#79`](https://github.com/PastVu/docs/pull/79) · `comment.giveForObj` | Дерево комментариев, различия анонимного и авторизованного ответов, удалённые комментарии, права и побочные эффекты чтения. |
| [`#80`](https://github.com/PastVu/docs/pull/80) · `photo.getByBounds` | Два режима выборки, GeoJSON, серверные кластеры, фильтрация по годам, различия в порядке координат и отсутствие пагинации в прямом режиме. |
| [`#81`](https://github.com/PastVu/docs/pull/81) · общие правила | Запросы `GET` и `POST`, параметры `method` и `params`, URL-кодирование, оболочки успешного ответа и ошибки, HTTP-статусы, `rid` и URL изображений. |

Все изменения подготовлены на русском и английском языках и приняты сопровождающими проекта.

### Как исследовался контракт

Для каждого метода я сопоставляла несколько источников:

1. Существующую публичную документацию.
2. Backend-код метода, проверки параметров и запросы к базе данных.
3. Клиентский код PastVu, если он помогал понять реальный сценарий использования.
4. Фактические запросы и ответы публичного API, включая ошибки и пограничные состояния.
5. Поведение английской и русской версий документации после сборки.

Например, для `photo.getByBounds` одного успешного ответа было недостаточно. Метод работает по-разному в режиме серверных кластеров и прямой выборки, использует GeoJSON с порядком координат `[lon, lat]`, а в отдельных объектах ответа встречается обратный порядок. Без проверки кода и нескольких сценариев это различие легко пропустить.

Подробный разбор первого этапа сохранён в отдельном кейсе [`photo.giveForPage`](/pastvu-photo-give-for-page-case/).

## Контрактный аудит

Для `comment.giveForObj` и `photo.getByBounds` я прошла ветви анонимного, авторизованного и модераторского доступа, разные типы геометрии, режимы кластеризации и граничные значения фильтров.

Во время аудита я разделяла три категории поведения:

- подтверждённый внешний контракт, который нужен пользователю API;
- внутренняя реализация, которую не стоит обещать внешнему клиенту;
- возможные дефекты сервера, которые нельзя закреплять в документации как норму.

Так в справочник не попали случайные детали моделей и ошибочное поведение. Вместо этого в нём зафиксированы проверяемые параметры, ограничения и различия между режимами работы.

Отдельный вопрос возник со статусом публичных методов. В коде десятки функций разрешены для вызова через внешний диспетчер, но признак `isPublic` сам по себе не означает, что команда поддерживает их как стабильный API для сторонних интеграций. Поэтому я документировала методы из официального списка, а расширение списка вынесла на согласование с сопровождающими.

## Внутренний Socket.IO

Внутренний action `comment.create` создаёт комментарий к фотографии или новости. У него не было OpenAPI-, AsyncAPI-схемы или типизированного интерфейса, поэтому request и response пришлось собирать по частям.

Я сопоставила:

- frontend-вызов и сборку payload;
- backend-валидацию и ошибки;
- модели комментария, фотографии и фрагмента изображения;
- реальные Socket.IO request/response frames из локального окружения.

Результатом стали [подробный reference-кейс](/pastvu-internal-api-case/) и [`comment.create.yaml`](/schemas/comment.create.yaml) — валидная схема AsyncAPI 3.1.0 с каналами, операцией, сообщениями, схемами и примерами.

Этот материал показывает другую сторону работы с API: не улучшение существующего справочника, а восстановление контракта, который раньше существовал только в коде и сетевом обмене.

## Проверка

Изменения проверялись на нескольких уровнях:

| Уровень | Что проверялось |
|---|---|
| Публичный API | Успешные ответы, ошибки, пустые результаты, фильтры, пагинация и пограничные параметры. |
| Код | Валидация, ветвление по правам и режимам, побочные эффекты и состав ответа. |
| Документация | Орфография, внутренние ссылки, сборка русской и английской версий Docusaurus. |
| AsyncAPI | Соответствие AsyncAPI 3.1.0 и проверка схемы через AsyncAPI CLI. |
| Git | Чистота diff, отдельные небольшие PR и синхронизация с актуальной веткой `main`. |

## Результат

Публичная документация PastVu теперь объясняет не только назначение четырёх методов, но и то, как сформировать запрос, прочитать успешный ответ, обработать ошибку и получить изображение. Сложные различия — дерево комментариев, GeoJSON, кластеры, фильтрация по годам и порядок координат — подтверждены кодом и реальными запросами.

Пять последовательных PR вошли в официальный справочник. Внутренний Socket.IO action оформлен как самостоятельный reference и машиночитаемая AsyncAPI-схема.
